**目标**：把 ex01–ex12 学到的东西拼成一个真正的多文件 C 项目，重点是**分离编译的思维方式**，不是写业务逻辑。

---

## 怎么跑

```bash
cd /d/c-learn/projects/contact

make            # 编译链接
make run        # 编译并运行（main.c 里有一整套 assert 测试）
make symbols    # 看符号表，理解链接到底干了什么
```

第一次跑一定是失败的 —— `contact.c` 里有 TODO，`main.c` 的断言会拦住你。做完一个 TODO 跑一次。

## 文件分工

| 文件 | 角色 | 你改吗 |
|---|---|---|
| `contact.h` | **接口**（合同）：类型、宏、函数声明、头文件守卫 | 不改，先读懂 |
| `contact.c` | **实现**：所有函数的具体逻辑 + `static` 私有辅助函数 | 主要在这里写 |
| `main.c` | **使用方**：只 include `contact.h`，完全不知道实现细节 | 不改 |
| `Makefile` | **构建规则**：把三个文件拼成 `app.exe` | 可改 |

## 这个项目要你掌握的六件事

### 1. 头文件守卫

```c
#ifndef CONTACT_H
#define CONTACT_H
...
#endif
```

没有它，如果 `contact.h` 被间接 include 两次（比如两个头文件互相包含），编译器会报「重复定义」。

### 2. 头文件只放声明，不放定义

一旦你在 `.h` 里写了函数定义（带函数体的那种），每个 include 它的 `.c` 都会生成一份该函数的副本，链接时立刻报 **multiple definition**。在单片机上这是最常见的构建错误之一。

例外：`static inline` 函数可以放头文件；`static` 全局变量可以放头文件（每个 `.c` 各有一份，互不影响）。

### 3. 分离编译三步走

```bash
gcc -c contact.c -o contact.o     # 编译：源码 -> 目标文件（还没有地址）
gcc -c main.c    -o main.o        # 编译
gcc contact.o main.o -o app.exe   # 链接：把 U（未定义）和 T（已定义）对上
```

跑一次 `make symbols`，你会看到 `main.o` 里所有 `contact_*` 都是 `U`（undefined），
而 `contact.o` 里都是 `T`（text，已定义）。链接器就是干「撮合」这件事的。

### 4. `static` 的两个含义

| 位置 | 含义 |
|---|---|
| `static` 全局变量 / 函数 | **只在本文件可见**（内部链接）—— 嵌入式里用来做「私有」 |
| `static` 局部变量 | **存储期是整个程序**（不在栈上），但作用域只在函数内 —— 用来做「状态记忆」 |

### 5. 错误码优于魔法值

所有接口返回 `contact_status_t`，成功就是 `CONTACT_OK == 0`。
不要在代码里到处写 `return -1;` 然后靠注释说明 -1 是什么意思。

### 6. 为什么序列化不能直接 `fwrite` 结构体

跑 `make run` 到最后一段，你会看到 `sizeof(ContactV2)` 比字段总和多了几个字节。
那几个字节是**填充垃圾**，里面是栈上残留的内存内容。
直接写出去等于泄漏内存内容 —— 这是真实存在过的安全漏洞类型。
